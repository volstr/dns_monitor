## Этап 2. Модель данных

Сущности раздела 4 ТЗ. Схему проектируешь сам, обязательства:

- Ключи `bigint`, моменты времени `timestamptz` в UTC (раздел 4.0).
- Адреса и подсети — типы `inet` / `cidr` PostgreSQL. Собственное поле Django, около 30 строк.
  `django-netfields` не подключать: запрос вхождения в продукте один.
- Проверка вхождения адреса в подсеть — один запрос с `>>=` и GiST-индексом. Не выгрузка списка
  в Python.
- **Выбор между `cidr` и `inet` зависит от открытого вопроса 13.3. Не решай сам, спроси.**
- Реестр адресов хранит **суточные корзины**: `домен + адрес + дата + факт наблюдения`. Писать
  каждое наблюдение нельзя: тысяча доменов даст под миллион строк в сутки, корзины дают три
  тысячи. Этого достаточно для графика 9.2 и требования 4.4.

Наследование настроек (раздел 5) — одна функция разрешения, возвращающая dataclass со значением
и его происхождением (`общая` / `от группы` / `своё`). Происхождение нужно интерфейсу, поэтому
оно часть результата, а не вычисляется в шаблоне.

**Готово, когда:** миграции накатываются с нуля, наследование покрыто тестами на всех трёх
уровнях, вхождение адреса в подсеть работает запросом и подтверждено `EXPLAIN`.

## Этап 3. Ядро проверки

Интерфейса ещё нет. Только домен и порты.

`Resolver` различает три исхода по требованию 6.1:

```python
class Outcome(Enum):
    ANSWERED    = "answered"      # есть записи
    NO_RECORDS  = "no_records"    # NXDOMAIN или NOERROR без записей
    UNAVAILABLE = "unavailable"   # ни один сервер не ответил

@dataclass(frozen=True, slots=True)
class ResolveResult:
    outcome: Outcome
    addresses: frozenset[str] = frozenset()
    answered_by: str | None = None
    error: str | None = None
```

`NO_RECORDS` — наблюдение: идёт в журнал и после N повторов порождает `RESOLVE_FAILED`.
`UNAVAILABLE` — «мы не смогли спросить»: реестр не трогается, событий нет, фиксируется
техническая ошибка. Различение должно держаться типом, а не дисциплиной.

Перебор серверов по порядку, таймаут `DNS_TIMEOUT_MS` на сервер и повторы — внутри адаптера.
Доменный код не знает, что серверов несколько.

Тестовый резолвер отдаёт заранее заданную последовательность ответов на каждое имя. Сценарий
«домен отдаёт по кругу два адреса из трёх» — это список результатов, повторяемый по кругу, плюс
подкрученные часы.

**Готово, когда:** критерии приёмки 1–13 зелёные. Критерий 13 (первый сервер молчит, второй
отвечает) проверяет адаптер и требует отдельного теста уровнем ниже — с подменой транспорта
`dnspython` или фиктивным DNS-сервером на локальном порту.

## Этап 4. Планировщик и ручная проверка

Команда `manage.py run_checker`: цикл с тиком раз в 5–10 секунд.

Тик забирает наступившие домены одним атомарным запросом с `FOR UPDATE SKIP LOCKED`, сдвигая
`next_check_at` на короткое резервирование порядка 30 секунд. Настоящее
`next_check_at = момент проверки + период группы` пишется по завершении проверки. Упавший процесс
не подвешивает домен: тот вернётся в выборку сам.

Разнос во времени задаётся один раз, при создании домена или импорте:
`next_check_at = now + random(0, период)`. Дальше сохраняется сам собой. Расписание живёт в БД,
поэтому перезапуск не собирает резолвы в пик — требование 11.1.

Резолвы исполняет `ThreadPoolExecutor` на `RESOLVE_CONCURRENCY` потоков.

Ключ `sched:lock:domain:{id}` нужен для гонки между плановой и ручной проверкой, не для
конкуренции экземпляров планировщика — её снимает `SKIP LOCKED`.

Кнопка «проверить домены группы» (11.6) резолвы не запускает: ставит затронутым доменам
`next_check_at = now()`, ближайший тик разберёт их с тем же ограничением параллелизма.

Плановая и ручная проверка вызывают одну функцию. Требование 11.6 «ручная проверка — настоящая
проверка» должно выполняться по построению, а не дублированием кода.

**Готово, когда:** тик вызывается из теста как обычная функция с явным моментом времени, сутки
прогоняются без `sleep`, два одновременных экземпляра не резолвят один домен дважды.

## Этап 5. События, инциденты, уведомления

Разделы 7 и 8 ТЗ.

Очередь исходящих — таблица в PostgreSQL: попытка, момент следующей попытки, последняя ошибка.
Экспоненциальная задержка — арифметика над моментом следующей попытки, конечное число попыток —
условие в запросе. Redis для этого не использовать: по 11.11 он не источник истины, а результат
доставки должен попадать в журнал (8.3).

Команда `manage.py run_notifier` — отдельный процесс: недоступность канала не должна занимать
потоки резолвера.

Окно слияния массовых событий (8.6) — единственная часть доставки, живущая в Redis.

В первой версии реализован Telegram. SMTP дописан позже, 2026-09-28: канал настоящий, но
уведомления в него ещё не маршрутизируются — это Q-D11. Вебхук остаётся заглушкой с тем же
протоколом.

**Готово, когда:** критерии приёмки 14–20 зелёные, падение канала не мешает проверкам идти.

## Этап 7. Виджеты

Три места клиентского кода, и только они:

1. Линейка подсети (11.4) — ручной SVG со склейкой перекрывающихся меток и раскрытием фрагмента
   по клику.
2. График реестра (9.2) — число корзин считается от ширины элемента, перестроение на
   `ResizeObserver`. Данные передаются рядом с элементом в `<script type="application/json">`.
3. Поле выбора группы с поиском (10.4).

**Готово, когда:** оба виджета покрыты Playwright. Он ставится из PyPI и браузеры тянет сам,
Node для этого не нужен.

## Тесты

Каждый пункт раздела 14 ТЗ — отдельный тест с номером пункта в имени. Это критерий готовности.

- `pytest` + `pytest-django`, PostgreSQL и Redis настоящие, поднимаются компоузом.
- Часы, резолвер и канал доставки подменяются через порты.
- Критерии 6–9 и 17 требуют прогона суток внутри теста. Это возможно только потому, что момент
  времени передаётся явно, — не ломай это ради удобства.
