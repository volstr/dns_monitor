# DNS monitoring

Сервис наблюдения за DNS-записями доменов. Код пишет ИИ-агент под ревью разработчика.

## Источники истины

- `guide/tz-dns-monitoring.md` — ТЗ. Истина по поведению продукта.
- `guide/dns-monitoring-prototype.html` — прототип экранов. Истина по вёрстке и CSS.
- `docs/plan.md` — этапы работы и проектные решения по каждому.
- `docs/glossary.md` — термины ТЗ и их идентификаторы в коде.
- `docs/questions.md` — открытые вопросы.

Прочитай ТЗ целиком до первой строки кода, особенно разделы 12, 13 и 14. При расхождении ТЗ и
прототипа делай по ТЗ и запиши расхождение в `docs/questions.md`.

## Стек. Не пересматривать и не предлагать альтернативы

| Слой | Выбор |
|---|---|
| Язык | Python 3.12 |
| Фреймворк | Django 5.2 LTS |
| БД | PostgreSQL 16, драйвер `psycopg` 3 |
| Состояние и кэш | Redis 7 |
| DNS | `dnspython` |
| Шаблоны | штатный язык шаблонов Django, не Jinja2 |
| Интерактив | HTMX + vanilla JS без сборщика |
| TOTP | `pyotp` |
| Ошибки | `sentry-sdk` |
| Сервер | `gunicorn` |
| Фоновая работа | долгоживущие management-команды |
| Очередь доставки | таблица в PostgreSQL |

Node.js в проекте нет — ни в образе, ни в репозитории. `package.json`, `node_modules` и сборщики
запрещены. HTMX лежит в `static/` файлом и коммитится.

Брокеров очередей нет: ни Celery, ни RQ, ни Huey, ни APScheduler, ни `django.tasks`.

## Границы слоёв

### View

Разрешено ровно четыре вещи: разобрать вход формой, вызвать **одну** функцию из `services/` или
`selectors/`, выбрать шаблон и передать результат, сделать редирект или поставить сообщение.

Запрещено: ветвления по доменным правилам, вычисление наследования настроек, `timezone.now()`,
обращения к Redis, `.save()`, циклы по queryset с решениями внутри.

Обработчики — классы с `get` и `post` (Q-D33). Роль задаётся базовым классом из
`apps/accounts/access.py`: `PublicView` — экран до входа, `MemberView` — для участника,
`AdminView` — только для администратора. Generic CBV Django (`ListView`, `DetailView`,
`UpdateView`) не использовать: они устроены вокруг `get_queryset()` и `form_valid()`, то есть
вокруг запрещённого выше.

Функция сервиса не знает про `HttpRequest`: принимает примитивы и dataclass, возвращает dataclass.
Понадобился `request` внутри сервиса — граница проведена неправильно.

Management-команды — тот же слой: разбирают аргументы и зовут сервис, логики не содержат.

### Типизация

- `mypy --strict` проходит по `core/`, `apps/*/services/`, `apps/*/selectors/`.
- Сервис никогда не возвращает наружу `dict`, кортеж или `QuerySet`.
- `@dataclass(frozen=True, slots=True)` — доменные значения и результаты операций.
- `TypedDict` — словарные структуры, уходящие в JSON: данные виджетов, полезная нагрузка события,
  контекст Sentry.
- `Enum` вместо строковых литералов для типов событий, статусов, режимов уведомлений и ролей.
- Отказ как штатный исход (разбор белого списка, разбор импорта, предохранители при правке
  участника) возвращается результатом с перечнем причин. Исключения — для настоящих аварий.

### Порты

В `core/ports/` протоколы, в `core/adapters/` реализации. Доменный код импортирует только протокол.

- `Clock` — единственное место с `timezone.now()`. Момент времени передаётся явно.
- `Resolver` — единственное место с `import dns`.
- `NotificationChannel` — требование 8.3.

У каждого порта две реализации: боевая и тестовая. `mock.patch` по путям импорта не использовать:
понадобился патч — значит зависимость не вынесена в порт.

## Redis

Полный перечень ключей и сроков жизни — таблица 11.11 ТЗ, отступать нельзя.

- Ключ без `TTL` — ошибка. Обёртка над клиентом должна физически не позволять его записать.
- Две логические базы: состояние (`noeviction`) и кэш, общего пространства ключей нет.
- Логин в ключах счётчика входа хешируется, срок жизни ставится только при первом увеличении.
- Недоступность Redis — авария по 11.13, а не режим пониженной функциональности.

## Фронтенд

Клиентский код существует ровно в трёх местах: линейка подсети (11.4), график реестра (9.2), поле
выбора группы с поиском (10.4). Больше нигде. Кажется, что нужен четвёртый — спроси.

Колонка «История» (11.5) рисуется серверным SVG, JS ей не нужен. Построчная валидация белого
списка (10.2) выполняется на сервере через HTMX с задержкой около 250 мс: дублировать разбор CIDR
в JS нельзя, реализация должна быть одна.

CSS прототипа переносится целиком, переменные там уже есть. Библиотеки компонентов не подключать.

## Docker

Файл разработчика — `docker-compose-dev.yml`. Сервисы: `postgres`, `redis`, `web`, `checker`,
`notifier`. Один образ, три разные команды.

Приложение работает под **UID=1000, GID=1000**:

- `groupadd -g 1000 app && useradd -u 1000 -g 1000 -m app`, директива `USER app` до `CMD`.
- Entrypoint не требует root: никаких `chown` на старте и переключения пользователя в рантайме.
- Пути, куда приложение пишет, создаются и назначаются пользователю на этапе сборки.
- Виртуальное окружение принадлежит тому же пользователю.
- Проверка: сгенерируй миграцию внутри контейнера и убедись, что она правится с хоста без sudo.

Миграции применяются отдельной командой, а не при старте `web`.

## Чего не делать

Раздел 12 ТЗ — закрытый список отклонённых решений, перечитывай перед каждым этапом. Сверх него:

- Периодическая задача на каждый домен. Расписание живёт в `next_check_at`, второго места нет.
- Обращение к `dnspython` вне адаптера, `timezone.now()` вне адаптера часов.
- Возврат `dict` или `QuerySet` из сервиса.
- Вычисления в шаблоне: всё считается до передачи в контекст.
- Заглушка без `TODO` с номером пункта ТЗ.
- Оптимизация сверх заявленного масштаба: тысяча доменов, минимальный период минута.

## Когда останавливаться и спрашивать

Не выбирай вариант сам, если это:

- открытый вопрос из раздела 13 ТЗ — особенно 13.3 (от него зависит тип колонки, то есть схема)
  и 13.8 (термин уйдёт в тексты уведомлений);
- расхождение ТЗ и прототипа;
- место, где ТЗ молчит, а решение видно пользователю;
- отступление от таблицы стека выше.

Вопросы пиши в `docs/questions.md` сразу, не копи до конца этапа: вопрос, где возник, варианты,
что выбрано временно и чем это грозит.
