# DNS monitoring

Сервис наблюдения за DNS-записями доменов: проверяет, какие адреса отдаёт домен, сравнивает их
с прошлым ответом и с заданным списком разрешённых адресов, ведёт журнал и присылает
уведомления дежурным.

Источники истины — `guide/tz-dns-monitoring.md` (поведение) и `guide/dns-monitoring-prototype.html`
(вёрстка). Решения по ходу работы записаны в `docs/`: `plan.md` — этапы, `glossary.md` — термины,
`questions.md` — вопросы и чем они закрыты. Правила для тех, кто пишет код, — в `CLAUDE.md`.

## Что должно быть на машине

Docker с плагином Compose. Больше ничего: Python, Node.js и пакеты ставить не нужно — всё живёт
в образе. Сборщиков фронтенда в проекте нет принципиально.

## Поднять окружение

```sh
cp .env.example .env
```

В `.env` нужно поправить два места, остальное годится как есть:

- `APP_UID` и `APP_GID` — ваши на хосте, `id -u` и `id -g`. Приложение в контейнере работает
  под этим пользователем, и без совпадения файлы, созданные внутри (например миграции), не
  будут правиться с хоста без `sudo`.
- `SESSION_SECRET` — любая случайная строка не короче 50 символов.

Дальше:

```sh
docker compose -f docker-compose-dev.yml up --build
```

Поднимается пять сервисов: `postgres`, `redis` и три процесса приложения из одного образа —
`web` (интерфейс), `checker` (проверки доменов) и `notifier` (доставка уведомлений).

**Миграции при старте не применяются** — намеренно, отдельной командой:

```sh
docker compose -f docker-compose-dev.yml run --rm web python manage.py migrate
```

Первый администратор заводится так — пароль спросят отдельно, в диалоге:

```sh
docker compose -f docker-compose-dev.yml run --rm web \
  python manage.py create_admin --email you@example.com --name "Ваше имя"
```

Команда работает только на установке, где администраторов ещё нет. Дальше участников заводят
приглашениями из интерфейса.

После этого интерфейс открывается на <http://localhost:8000>.

### Статика

`htmx.min.js` и шрифты лежат в `static/` файлами и коммитятся — внешних зависимостей во время
работы у приложения нет вовсе: установки бывают в закрытом контуре. Что откуда взято и какие у
этого лицензионные обязательства — в [`static/README.md`](static/README.md).

### Админка Django

Есть, но **только в режиме разработчика** — на <http://localhost:8000/admin/>, вход общий, тем
же администратором. В `prod` её нет вовсе: приложение подключено в `config/settings/dev.py`, а
маршрут заводится по наличию приложения, а не по `DEBUG`.

Помните, чем за неё платят: правка через админку минует сервисы, а с ними предохранители 3.1,
запись в журнал с автором, завершение сессий при смене почты и разбор белого списка. Расхождение
вроде «участник отключён, а в журнале ничего» после такой правки объясняется именно этим. Разбор
и перечень обходимого — в `config/admin.py` и Q-D35.

### Первое, что нужно сделать в интерфейсе

Заполнить **список DNS-серверов** в общих настройках. На свежей установке он пуст, и проверки
без него невозможны — приложение говорит об этом на каждом экране, но искать причину в логах
`checker` не стоит.

## Запустить тесты

```sh
docker compose -f docker-compose-dev.yml run --rm web pytest
```

PostgreSQL и Redis настоящие, из того же компоуза; логические базы Redis у тестов свои, чтобы
не делить состояние с работающим приложением. Часы, резолвер и канал доставки подменяются через
порты — `mock.patch` по путям импорта в проекте не используется.

Браузерные проверки (`tests/e2e/`) идут там же: Playwright с Chromium уже в образе разработчика.
Пропустить их — `pytest -m "not e2e"`.

Проверки качества, те же, что перед каждым коммитом:

```sh
docker compose -f docker-compose-dev.yml run --rm web ruff check .
docker compose -f docker-compose-dev.yml run --rm web mypy
```

## Работа с миграциями

Сгенерировать после правки моделей:

```sh
docker compose -f docker-compose-dev.yml run --rm web python manage.py makemigrations
```

Файл создаётся внутри контейнера, но принадлежит вам — за это отвечают `APP_UID` и `APP_GID`.
Если правка требует `sudo`, они заданы неверно.

Применить — командой `migrate` выше. В боевой установке это отдельный шаг развёртывания, а не
часть старта `web`: одновременный старт нескольких экземпляров не должен превращаться в гонку
миграций.

## Эксплуатация

**Процессы.** `checker` и `notifier` — долгоживущие команды, а не задания планировщика. Брокеров
очередей в проекте нет: расписание проверок живёт в поле `next_check_at`, очередь доставки — в
таблице PostgreSQL. Оба процесса безопасно перезапускать и можно запускать в нескольких
экземплярах: домены разбираются через `FOR UPDATE SKIP LOCKED`, один домен резолвится один раз.

**Журнал.** Формат — JSON, по строке на запись, в общий поток. Поля `level`, `logger`, `run` и
всё, что процесс добавил от себя: `domain`, `component`, `notification`. `run` — идентификатор
обхода: по нему собираются все записи одного цикла проверок. В режиме разработчика формат
человекочитаемый, потому что этот журнал читают глазами.

Время в поле `ts` — местное, по `APP_TIME_ZONE`, и **со смещением**:
`2026-09-27T12:33:10.237+03:00`. Смещение стоит там не для красоты: без него метку нельзя ни
сравнить с журналом другой системы, ни правильно прочитать после того, как пояс установки
поменяли. Решение и его разбор — Q-D34.

**Хранение.** Журнал событий и реестр адресов убираются по срокам из общих настроек (по
умолчанию 90 суток и бессрочно). Уборка идёт сама, внутри `checker`, не чаще раза в час. После
того как срок поменяли, можно не ждать:

```sh
docker compose -f docker-compose-dev.yml run --rm web python manage.py purge_history
```

**Redis обязателен.** Его недоступность — авария, а не режим пониженной функциональности:
проверки останавливаются, интерфейс отвечает `503`, дежурным уходит сообщение. Данные в Redis
не источник истины — потеря его содержимого сбрасывает счётчики, кулдауны и блокировки, но не
трогает домены, события, реестр и участников.

**Sentry необязателен.** Пустой `SENTRY_DSN` — нормальный режим: приложение работает и ничего
никуда не отправляет. Заданный DSN неверного формата, наоборот, останавливает старт. В Sentry
уходят отказы инфраструктуры и ошибки приложения, но не доменные события: `NXDOMAIN`, адрес вне
списка, ошибка ввода и неудачный вход туда не идут никогда.

## Переменные окружения

Полный перечень с пояснениями — в `.env.example`. Приложение проверяет их при старте и падает с
именем переменной, если обязательная не задана или не проходит проверку формата. Пустые
`SMTP_HOST`, `SENTRY_DSN` и `TELEGRAM_BOT_TOKEN` — рабочий режим, а не ошибка.

Часовой пояс показа: `APP_TIME_ZONE`. Если не задан, берётся системный (`TZ`, затем
`/etc/localtime`), а если и его нет — UTC. Хранится время всегда в UTC, меняется только показ.

Версия сборки: `APP_RELEASE`. Необязательна, уходит в Sentry релизом — без неё не понять, какое
развёртывание сломало работу.
