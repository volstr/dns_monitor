# DNS monitoring

Сервис наблюдения за DNS-записями доменов: проверяет, какие адреса отдаёт домен, сравнивает их
с прошлым ответом и с заданным списком разрешённых адресов, ведёт журнал и присылает
уведомления дежурным.

Источники истины — `guide/tz-dns-monitoring.md` (поведение) и `guide/dns-monitoring-prototype.html`
(вёрстка). Решения по ходу работы записаны в `docs/`: `plan.md` — этапы, `glossary.md` — термины,
`questions.md` — вопросы и чем они закрыты. Правила для тех, кто пишет код, — в `CLAUDE.md`.

## Что должно быть на машине

Docker с плагином Compose. Больше ничего: Python, Node.js и пакеты ставить не нужно — всё живёт
в образе. Сборщиков фронтенда в проекте нет принципиально.

## Два компоуза

Файлов два, и они намеренно разные:

| | `docker-compose.yml` | `docker-compose-dev.yml` |
|---|---|---|
| Для чего | боевая установка | рабочая машина |
| Исходники | берутся из образа | подложены в контейнер, правка подхватывается сразу |
| Зависимости | только рабочие | с `pytest`, `mypy`, `ruff`, браузером Playwright |
| Сервер | `gunicorn` за `nginx` | `runserver` |
| Статика | собирается `collectstatic`, отдаёт `nginx` | отдаёт `runserver` |
| Перезапуск | `unless-stopped` — сама после перезагрузки машины | вручную |
| Порты наружу | только `80` у `nginx` | `8000` у приложения |

Боевой файл называется `docker-compose.yml`, потому что это имя Compose берёт по умолчанию:
на сервере команды короткие и без флагов. Команды разработчика, наоборот, **всегда** с
`-f docker-compose-dev.yml`. Голый `docker compose up` на рабочей машине возьмёт боевой файл:
имя проекта у них общее, и он заменит контейнеры разработчика боевыми. Данные при этом целы —
тома те же, — но поднятое окажется не тем, что ожидалось.

## Боевая установка

### 1. Что задать в `.env`

```sh
cp .env.example .env
```

Четыре значения обязаны отличаться от того, что годится для разработки:

- **`ALLOWED_HOSTS`** — имена, под которыми установка отвечает, через запятую:
  `dns.example.com, 10.20.0.7`. Без неё приложение не стартует и скажет об этом. Так сделано
  намеренно: Django при `DEBUG=False` отверг бы любой запрос, и установка выглядела бы
  сломанной, не называя причины.
- **`SESSION_SECRET`** — случайная строка не короче 50 символов, своя. Со сменой значения все
  выданные сессии становятся недействительными, поэтому менять её потом дорого.
- **`POSTGRES_PASSWORD`** — свой. Компоуз не поднимется, если переменная не задана вовсе, но
  подставленный из примера `dns_monitoring` он отличить не может: это уже на вас.
- **`APP_BASE_URL`** — адрес, по которому установку открывает человек. Он уходит в ссылки
  уведомлений, и `http://localhost:8000` из примера сделает их бесполезными с телефона.

`DJANGO_SETTINGS_MODULE` трогать не нужно: боевой компоуз ставит `config.settings.prod` сам,
что бы ни осталось в файле после копирования с рабочей машины.

`APP_UID` и `APP_GID` в бою значения не имеют — они нужны только там, где каталог проекта
подложен в контейнер.

### 2. Первое развёртывание

```sh
docker compose up -d --build
docker compose run --rm web python manage.py migrate
docker compose run --rm web python manage.py collectstatic --noinput
docker compose run --rm web python manage.py create_admin --email you@example.com --name "Ваше имя"
```

Поднимается шесть сервисов: `postgres`, `redis`, `nginx` и три процесса приложения из одного
образа — `web` (интерфейс), `checker` (проверки доменов) и `notifier` (доставка уведомлений).

Четыре команды, а не одна, и это не лень:

- **`migrate` отдельно от старта** — требование, а не упущение. Одновременный запуск нескольких
  экземпляров не должен превращаться в гонку миграций.
- **`collectstatic`** наполняет том, из которого читает `nginx`. Пока он не выполнен, страницы
  придут без оформления: при `DEBUG=False` Django статику не отдаёт вовсе.
- **`create_admin`** спросит пароль отдельно, в диалоге, — он не попадёт ни в историю команд,
  ни в журнал. Команда работает только там, где администраторов ещё нет; дальше участников
  заводят приглашениями из интерфейса. Для развёртывания скриптом пароль можно передать
  переменной `ADMIN_PASSWORD`, но тогда он попадает в окружение процесса со всеми вытекающими.

После этого интерфейс открывается на том адресе, что записан в `ALLOWED_HOSTS`.

### 3. Обновление версии

```sh
docker compose up -d --build
docker compose run --rm web python manage.py migrate
docker compose run --rm web python manage.py collectstatic --noinput
```

`collectstatic` нужен каждый раз: том со статикой переживает пересборку образа, и без этого
шага останется прежний CSS.

### TLS

В `deploy/nginx.conf` его нет. Сертификаты выпускает и продлевает установка, а не репозиторий:
прописать пути к чужим файлам значит сделать компоуз неподнимаемым у всех, кроме одного.

Когда сертификаты появятся — добавьте `server` на 443 и оставьте на 80 перенаправление. После
этого достаточно, чтобы `APP_BASE_URL` начинался с `https://`: приложение само включит
защищённые куки. Схему запроса оно узнаёт от `nginx` через `X-Forwarded-Proto`, и доверять
этому заголовку можно ровно потому, что порта наружу у `web` нет — **не открывайте его**, иначе
заголовок станет подделываемым.

### За внешним прокси

Установку можно поставить за ещё один nginx, Nginx Proxy Manager, Traefik или балансир
хостинга. Встроенный `nginx` при этом остаётся: он отдаёт статику и знает, как устроено
приложение, а внешний занимается именами, сертификатами и маршрутизацией.

**Порт.** Встроенный `nginx` публикует `${HTTP_PORT:-80}`. Внешнему прокси нужен тот же 80 (и
443), поэтому на одном сервере они столкнутся — `address already in use`. Два выхода:

```sh
# 1. Отдать внешнему прокси 80 и 443, свой увести на другой порт.
#    В .env: HTTP_PORT=127.0.0.1:8080   ← адрес обязателен, иначе порт откроется наружу
```

```yaml
# 2. Лучше: не публиковать порт вовсе, а соединить их общей сетью Docker.
#    В docker-compose.override.yml рядом с боевым файлом:
services:
  nginx:
    ports: !reset []
    networks: [default, proxy]
networks:
  proxy:
    external: true
    name: proxy             # как сеть внешнего прокси называется на самом деле
```

Во втором случае внешний прокси направляет трафик на `dns-monitoring-nginx-1:80` по имени
контейнера, и порт на хосте не открывается вовсе. Это надёжнее: приложение недоступно в обход
прокси по определению, а не по договорённости.

**Что ещё придётся задать.** Три вещи, и без них всё выглядит работающим, но ведёт себя не так:

- `ALLOWED_HOSTS` — имя, под которым установку открывает человек, то есть то, что внешний
  прокси ставит в заголовок `Host`. Не имя контейнера.
- `APP_BASE_URL` — внешний адрес со схемой `https://`, если TLS завершает внешний прокси. От
  него зависят ссылки в уведомлениях и включение защищённых кук.
- На внешнем прокси — передача `X-Forwarded-For` и `X-Forwarded-Proto`. NPM и штатный nginx
  шлют их сами; проверьте, что не отключены.

**Чего делать не нужно.** Встроенный `nginx` уже разбирает эти заголовки: он доверяет им
только от частных адресов (`10/8`, `172.16/12`, `192.168/16`, `127/8`) и подставляет настоящий
адрес клиента и настоящую схему. Запрос с публичного адреса такими заголовками ничего о себе
подменить не может. Если ваш внешний прокси стоит на публичном адресе — допишите его в
`set_real_ip_from` и в блок `geo` в `deploy/nginx.conf`.

### Что переживает перезапуск, а что нет

Домены, события, реестр адресов и участники живут в PostgreSQL, в томе `postgres-data`. Redis
намеренно без сохранения на диск: по 11.11 он не источник истины. Цена известна и принята —
перезапуск сбрасывает счётчики попыток входа, кулдауны, блокировки планировщика и **сессии**,
то есть всем придётся войти заново.

## Среда разработчика

```sh
cp .env.example .env
```

Здесь достаточно поправить два места, остальное годится как есть:

- `APP_UID` и `APP_GID` — ваши на хосте, `id -u` и `id -g`. Приложение в контейнере работает
  под этим пользователем, и без совпадения файлы, созданные внутри (например миграции), не
  будут правиться с хоста без `sudo`.
- `SESSION_SECRET` — любая случайная строка не короче 50 символов.

`ALLOWED_HOSTS` можно оставить пустой: `localhost`, `127.0.0.1` и `[::1]` добавляются сами.

Дальше:

```sh
docker compose -f docker-compose-dev.yml up --build
docker compose -f docker-compose-dev.yml run --rm web python manage.py migrate
docker compose -f docker-compose-dev.yml run --rm web \
  python manage.py create_admin --email you@example.com --name "Ваше имя"
```

Поднимается пять сервисов: `postgres`, `redis`, `web`, `checker` и `notifier`. `nginx` здесь не
нужен — `runserver` отдаёт статику сам, поэтому `collectstatic` в этом списке и отсутствует.

Интерфейс открывается на <http://localhost:8000>.

### Админка Django

Есть, но **только в режиме разработчика** — на <http://localhost:8000/admin/>, вход общий, тем
же администратором. В `prod` её нет вовсе: приложение подключено в `config/settings/dev.py`, а
маршрут заводится по наличию приложения, а не по `DEBUG`.

Помните, чем за неё платят: правка через админку минует сервисы, а с ними предохранители 3.1,
запись в журнал с автором, завершение сессий при смене почты и разбор белого списка. Расхождение
вроде «участник отключён, а в журнале ничего» после такой правки объясняется именно этим. Разбор
и перечень обходимого — в `config/admin.py` и Q-D35.

### Запустить тесты

```sh
docker compose -f docker-compose-dev.yml run --rm web pytest
```

PostgreSQL и Redis настоящие, из того же компоуза; логические базы Redis у тестов свои, чтобы
не делить состояние с работающим приложением. Часы, резолвер и канал доставки подменяются через
порты — `mock.patch` по путям импорта в проекте не используется.

Браузерные проверки (`tests/e2e/`) идут там же: Playwright с Chromium уже в образе разработчика.
Пропустить их — `pytest -m "not e2e"`.

Проверки качества, те же, что перед каждым коммитом:

```sh
docker compose -f docker-compose-dev.yml run --rm web ruff check .
docker compose -f docker-compose-dev.yml run --rm web mypy
```

### Работа с миграциями

Сгенерировать после правки моделей:

```sh
docker compose -f docker-compose-dev.yml run --rm web python manage.py makemigrations
```

Файл создаётся внутри контейнера, но принадлежит вам — за это отвечают `APP_UID` и `APP_GID`.
Если правка требует `sudo`, они заданы неверно.

## Настройка после установки

Одинаково и в бою, и на рабочей машине.

### Первое, что нужно сделать в интерфейсе

Заполнить **список DNS-серверов** в общих настройках. На свежей установке он пуст, и проверки
без него невозможны — приложение говорит об этом на каждом экране, но искать причину в логах
`checker` не стоит.

### Куда Telegram отправляет сообщения

Токен бота и идентификатор чата — **разные** значения, и лежат они в разных местах: токен в
`.env` переменной `TELEGRAM_BOT_TOKEN`, идентификатор чата — на экране «Настройки». Перепутать их
легко, потому что оба выдаёт @BotFather; приложение такую путаницу отвергает при сохранении.

Идентификатор чата получают в три шага:

1. Напишите боту любое сообщение — или добавьте его в группу либо канал и напишите там. Без
   этого Telegram не считает, что переписка началась, и следующий шаг вернёт пустой ответ.
2. Откройте `https://api.telegram.org/bot<ВАШ_ТОКЕН>/getUpdates` — прямо в браузере.
3. Возьмите из ответа `chat.id`. У личной переписки это положительное число, у группы
   отрицательное, у канала начинается с `-100`. Впишите его в поле «Идентификатор чата» и
   нажмите «Отправить тестовое» — сообщение должно прийти сразу, а при неудаче экран покажет
   ответ Telegram дословно.

В адресе из второго шага виден токен: не открывайте его при посторонних и не оставляйте в
истории общего браузера.

### Статика

`htmx.min.js` и шрифты лежат в `static/` файлами и коммитятся — внешних зависимостей во время
работы у приложения нет вовсе: установки бывают в закрытом контуре. Что откуда взято и какие у
этого лицензионные обязательства — в [`static/README.md`](static/README.md).

В режиме разработчика файлы отдаёт `runserver` прямо отсюда. В бою `DEBUG=False`, и Django
статику не отдаёт вовсе — это работа веб-сервера: `collectstatic` складывает её в том, а
`nginx` читает его только на чтение.

## Эксплуатация

**Каналы доставки.** Работают Telegram и почта. Событие уходит **во все настроенные сразу**:
канал считается настроенным, когда задан и адресат (на экране «Настройки»), и подключение (в
окружении — `TELEGRAM_BOT_TOKEN`, `SMTP_HOST` с `SMTP_FROM`). Незаданное — нормальный режим, а
не ошибка. В журнале у события столько строк доставки, сколько каналов, и у каждой свой исход.
Вебхук пока заглушка и в развозке не участвует.

**Процессы.** `checker` и `notifier` — долгоживущие команды, а не задания планировщика. Брокеров
очередей в проекте нет: расписание проверок живёт в поле `next_check_at`, очередь доставки — в
таблице PostgreSQL. Оба процесса безопасно перезапускать и можно запускать в нескольких
экземплярах: домены разбираются через `FOR UPDATE SKIP LOCKED`, один домен резолвится один раз.

**Журнал.** Формат — JSON, по строке на запись, в общий поток. Поля `level`, `logger`, `run` и
всё, что процесс добавил от себя: `domain`, `component`, `notification`. `run` — идентификатор
обхода: по нему собираются все записи одного цикла проверок. В режиме разработчика формат
человекочитаемый, потому что этот журнал читают глазами.

Время в поле `ts` — местное, по `APP_TIME_ZONE`, и **со смещением**:
`2026-09-27T12:33:10.237+03:00`. Смещение стоит там не для красоты: без него метку нельзя ни
сравнить с журналом другой системы, ни правильно прочитать после того, как пояс установки
поменяли. Решение и его разбор — Q-D34.

Журналы контейнеров в боевом компоузе ограничены по размеру: пять файлов по 10 МБ на службу.
Без этого `docker logs` растёт, пока не кончится диск, — а `checker` пишет строку на каждый обход.

**Хранение.** Журнал событий и реестр адресов убираются по срокам из общих настроек (по
умолчанию 90 суток и бессрочно). Уборка идёт сама, внутри `checker`, не чаще раза в час. После
того как срок поменяли, можно не ждать:

```sh
docker compose run --rm web python manage.py purge_history
```

Команды этого раздела написаны для боевой установки. На рабочей машине к каждой добавляется
`-f docker-compose-dev.yml`.

**Redis обязателен.** Его недоступность — авария, а не режим пониженной функциональности:
проверки останавливаются, интерфейс отвечает `503`, дежурным уходит сообщение. Данные в Redis
не источник истины — потеря его содержимого сбрасывает счётчики, кулдауны и блокировки, но не
трогает домены, события, реестр и участников.

**Sentry необязателен.** Пустой `SENTRY_DSN` — нормальный режим: приложение работает и ничего
никуда не отправляет. Заданный DSN неверного формата, наоборот, останавливает старт. В Sentry
уходят отказы инфраструктуры и ошибки приложения, но не доменные события: `NXDOMAIN`, адрес вне
списка, ошибка ввода и неудачный вход туда не идут никогда.

### Переменные окружения

Полный перечень с пояснениями — в `.env.example`. Приложение проверяет их при старте и падает с
именем переменной, если обязательная не задана или не проходит проверку формата. Пустые
`SMTP_HOST`, `SENTRY_DSN` и `TELEGRAM_BOT_TOKEN` — рабочий режим, а не ошибка.

Имена, под которыми приложение отвечает: `ALLOWED_HOSTS`, через запятую —
`dns.example.com, 10.20.0.7`. В боевом режиме обязательна: без неё Django отверг бы любой
запрос, поэтому приложение лучше не стартует и говорит об этом. В режиме разработчика
необязательна — `localhost`, `127.0.0.1` и `[::1]` добавляются сами.

Из `APP_BASE_URL` имя **не выводится**. Это разные величины: `APP_BASE_URL` — адрес, по
которому установку открывает человек и который уходит в ссылки уведомлений (8.4), а отвечать
приложение может ещё и по внутреннему имени или за обратным прокси.

Часовой пояс показа: `APP_TIME_ZONE`. Если не задан, берётся системный (`TZ`, затем
`/etc/localtime`), а если и его нет — UTC. Хранится время всегда в UTC, меняется только показ.

Версия сборки: `APP_RELEASE`. Необязательна, уходит в Sentry релизом — без неё не понять, какое
развёртывание сломало работу.

Число рабочих процессов `gunicorn`: `GUNICORN_WORKERS`, по умолчанию три. Порт, который слушает
`nginx`: `HTTP_PORT`, по умолчанию 80. Обе нужны только боевому компоузу.
