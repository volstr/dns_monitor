## 1. Назначение

Сервис периодически резолвит список наблюдаемых доменных имён, сравнивает полученные IP-адреса с предыдущим состоянием и со списком разрешённых адресов и подсетей, и при расхождении отправляет уведомление в Telegram.

Ключевая задача, вокруг которой строится всё остальное: **узнать, что домен стал указывать не туда, раньше, чем это заметят пользователи или злоумышленник успеет закрепиться.**

Вторая задача, менее срочная, но постоянная: **вести историю адресов каждого домена**, чтобы можно было оценить, какой адрес для домена живой, а какой давно не отдаётся.

Аудитория — системные администраторы, DevOps- и безопасность-инженеры. Интерфейс на русском языке.

## 2. Глоссарий

Термины обязательны к использованию в коде, API и интерфейсе. Синонимы не вводить.

| Термин | Значение |
|---|---|
| **Домен** | Наблюдаемое доменное имя. Единица наблюдения. |
| **Группа** | Набор доменов с общим расписанием и режимом уведомлений. |
| **Проверка** | Один цикл резолва одного домена. |
| **Ответ** | Множество IP-адресов, полученных в одной проверке. |
| **Разрешённые адреса и подсети** | Белый список записей домена. Запись — либо отдельный IP, либо подсеть в нотации CIDR. |
| **Запись списка** | Один элемент белого списка. |
| **Актуальный адрес** | Адрес, который отдавался хотя бы раз за порог актуальности. |
| **Порог актуальности** | Время, после которого молчащий адрес считается пропавшим. Настройка группы или общая. |
| **Актуальный набор** | Множество актуальных адресов домена на текущий момент. |
| **Статус адреса** | Одно из трёх: «Решён», «Не решён», «Не актуален». См. раздел 6. |
| **Реестр адресов** | История всех адресов, когда-либо отданных доменом, с датами первого и последнего обнаружения. |
| **Инцидент** | Период, в течение которого у домена есть хотя бы один нерешённый адрес. |
| **Событие** | Запись в журнале. Может порождать уведомление, а может и не порождать. |
| **Уведомление** | Сообщение, отправленное в канал доставки. |

Отдельно: слово «разрешённый» в интерфейсе означает **дозволенный** (белый список). Статус адреса называется **«Решён»**. Это разные вещи, не путать в коде: `allowlist` против `status`.

## 3. Роли и доступ

Две роли.

- **Администратор** — полный доступ: домены, группы, настройки, участники.
- **Наблюдатель** — только чтение: домены, реестр, журнал, группы. Не меняет ничего, включая собственную роль.

Требования к аутентификации:

- Вход по почте и паролю. Почта служит логином.
- Пароли хранятся только в виде хеша современного алгоритма с солью. Восстановление пароля невозможно, только выдача нового.
- Срок сессии настраивается: 8 часов / 7 дней / 30 дней.

**Второй фактор.** Управляется переменной окружения `AUTH_2FA_ENABLED` (см. 11.10), а не настройкой в интерфейсе. Это свойство установки, а не продукта: администратор приложения не должен иметь возможности отключить второй фактор для всех, войдя под угнанной учётной записью.

Следствия для интерфейса:

- При выключенной переменной форма входа состоит из двух полей: почта и пароль. Поля кода на экране **нет вообще** — не скрытого, не заблокированного, а отсутствующего.
- При включённой переменной поле кода присутствует и обязательно к заполнению.
- Участник, у которого приложение-аутентификатор ещё не привязано, после проверки пароля попадает на обязательную привязку и до её завершения не получает доступа к остальным экранам.
- На вкладке «Пользователи» состояние второго фактора показывается **только для чтения**, с пометкой о том, что оно задано в окружении. Переключателя там быть не должно.
- Один и тот же код TOTP не принимается дважды. Признак использования хранится в Redis, см. 11.11.

**Блокировка входа.** На 15 минут после N неудачных попыток. N задаётся в настройках продукта, по умолчанию 5. Счёт ведётся по паре «логин + IP» и хранится **в Redis, а не в таблице БД**: это эфемерные данные с естественным сроком жизни, и складывать их в БД значит заводить строки, которые потом придётся чистить заданием по расписанию.

Создание участников — три способа, доступность зависит от наличия почтового сервера:

1. **Письмом.** Доступно, только если в окружении задан `SMTP_HOST` (см. 11.10). Ссылка-приглашение уходит письмом. Настроить почту из интерфейса нельзя — при незаданной переменной способ показывается выключенным с объяснением, к кому обращаться.
2. **Ссылкой.** Доступно всегда. Генерируется одноразовая ссылка со сроком жизни (24 часа / 7 дней / 30 дней). Ссылка показывается администратору один раз и остаётся доступной для копирования из списка участников, пока не открыта. Открывший задаёт себе пароль сам.
3. **Заданием пароля.** Доступно всегда. Администратор задаёт пароль вручную, система показывает его один раз. Флаг «Потребовать смену при первом входе» включён по умолчанию.

Список участников показывает состояние доступа, а не только дату входа: «Активен», «Ссылка не открыта» (с датой истечения), «Пароль выдан, не менялся».

### 3.1 Редактирование участника

Открывается по имени участника или кнопке в строке. Роль **не меняется прямо в таблице**: случайный промах по выпадающему списку не должен выдавать права администратора.

**Редактируемые поля:** имя, почта, роль.

Смена почты — чувствительное действие: она же логин. При смене все сессии участника завершаются, а если почта настроена, уведомление уходит и на прежний, и на новый адрес.

**Действия с доступом:**

- *Сбросить пароль.* Предлагает те же три способа передачи, что и приглашение (письмом, ссылкой, заданием пароля), с той же зависимостью от `SMTP_HOST`. Прежний пароль перестаёт действовать немедленно, сессии завершаются.
- *Завершить все сессии.* Без смены пароля. Нужно, когда участник забыл выйти на чужом устройстве.
- *Отвязать аутентификатор.* Доступно только при `AUTH_2FA_ENABLED=true`. Нужно, когда человек потерял телефон: при следующем входе он привяжет приложение заново. Действие записывается в журнал с указанием того, кто его выполнил.

**Отключение против удаления.**

- *Отключение* — основной способ прекратить доступ. Вход прекращается в течение 30 секунд (срок жизни кэша роли, см. 11.12). Записи журнала о действиях участника сохраняются, роль можно вернуть.
- *Удаление* доступно **только для участников, которые ни разу не входили** — то есть для непринятых приглашений. Участник, на которого ссылаются записи журнала, удалению не подлежит: иначе история потеряет авторство и перестанет быть пригодной для разбора.

**Предохранители.** Каждый проверяется и на стороне API, а не только в интерфейсе:

- Нельзя понизить собственную роль и нельзя отключить самого себя.
- Нельзя отключить или понизить **последнего** администратора. Установка без администратора необратима: некому вернуть права.
- Нельзя назначить роль выше собственной. Наблюдатель вообще не имеет доступа к этому разделу.

Все изменения участников записываются в журнал: кто, кого, что изменил и когда.

## 4. Доменная модель

Схему БД проектирует разработчик. Ниже — логические сущности и их существенные атрибуты.

### 4.0 Соглашения по типам данных

Обязательны для всех таблиц.

**Ключи.** Все первичные и внешние ключи — `bigint`. Без исключений, в том числе для таблиц, где заведомо мало строк: единый тип ключа избавляет от ошибок в соединениях и от миграций задним числом, когда «маленькая» таблица неожиданно выросла. Способ генерации (автоинкремент, последовательность, снежинка) — на усмотрение разработчика.

**Текст.** Все текстовые поля — `varchar(n)` с явно указанной длиной. Тип без ограничения длины не использовать. Причина практическая: неограниченное поле рано или поздно попадёт в сообщение Telegram или в выгрузку и сломает лимит, а ограничение на уровне интерфейса легко обойти через API.

Рекомендуемые длины:

| Поле | Тип | Обоснование |
|---|---|---|
| Доменное имя | `varchar(255)` | предел FQDN — 253 символа |
| Название группы | `varchar(120)` | |
| Комментарий домена и группы | `varchar(2000)` | попадает в уведомление, длиннее бессмысленно |
| Почта участника | `varchar(320)` | предел адреса по RFC |
| Имя участника | `varchar(160)` | |
| Хеш пароля | `varchar(255)` | с запасом на смену алгоритма |
| Роль, тип события, режим уведомлений, статус доставки | `varchar(32)` | см. ниже о перечислениях |
| IP-адрес | `varchar(45)` | предел IPv6 с зоной |
| Запись белого списка | `varchar(49)` | IPv6 с длиной префикса |
| Токен приглашения | `varchar(64)` | |
| Идентификатор сообщения в канале доставки | `varchar(64)` | нужен, чтобы отвечать в ветку |
| Ссылка | `varchar(2048)` | |
| Причина ошибки разбора строки импорта | `varchar(500)` | |

**Перечисления.** Хранить как `varchar(32)` с ограничением допустимых значений, а не нативным типом-перечислением СУБД. Добавление значения в нативный тип требует миграции, а типы событий и каналов доставки будут пополняться.

**Время.** Метки времени — тип с часовым поясом, хранение в UTC, отображение в часовом поясе установки. Все интервалы (период проверки, порог актуальности, интервал напоминаний) хранить в секундах целым числом, а не строкой.

**Адреса.** Если выбранная СУБД имеет специализированный тип для IP-адресов и подсетей, использовать его: это даёт индексируемую проверку вхождения без выгрузки списка в приложение. При отсутствии такого типа — `varchar` указанной выше длины, а проверка вхождения выполняется в приложении.

### 4.1 Общие настройки (одна запись на установку)

- Период проверки по умолчанию.
- Порог актуальности по умолчанию.
- Режим уведомлений по умолчанию.
- Флаг «сообщать о возврате в норму» по умолчанию.
- Интервал повторных напоминаний по умолчанию.
- Окно и порог слияния массовых событий.
- Список DNS-серверов (упорядоченный).
- Количество повторов при ошибке резолва.
- Срок хранения журнала событий.
- Срок хранения реестра адресов.

### 4.2 Группа

- Название, комментарий.
- Период проверки: конкретное значение **или** «по умолчанию».
- Порог актуальности: конкретное значение **или** «по умолчанию».
- Режим уведомлений: конкретное значение **или** «по умолчанию».
- Флаг «сообщать о возврате в норму»: конкретное значение **или** «по умолчанию».
- Интервал повторных напоминаний: конкретное значение **или** «по умолчанию».

Группа **не содержит** разрешённых адресов и подсетей.

### 4.3 Домен

- Имя (в нормализованном виде, см. 10.1).
- Группа (может отсутствовать).
- Комментарий.
- Список разрешённых адресов и подсетей.
- Типы запрашиваемых записей: A, AAAA, CNAME (флаги).
- Флаг «наблюдение включено».

Домен **не содержит** периода проверки и режима уведомлений — они берутся у группы.

### 4.4 Запись реестра адресов

Уникальна по паре «домен + IP-адрес».

- Момент первого обнаружения.
- Момент последнего обнаружения.
- Данных о промежуточных наблюдениях достаточно для построения графика по суткам (см. 9.2).

### 4.5 Событие

- Домен, тип, момент, полезная нагрузка (какие адреса затронуты).
- Ссылка на связанное уведомление, если оно отправлялось.
- Ссылка на инцидент, если событие к нему относится.

### 4.6 Инцидент

- Домен, момент открытия, момент закрытия (пустой, если открыт).
- Идентификатор отправленного сообщения в канале доставки — нужен, чтобы ответить на него при закрытии и при напоминании.
- Момент последнего отправленного сообщения по инциденту — от него отсчитывается интервал напоминаний.

## 5. Наследование настроек

Цепочка ровно двухступенчатая: **общие настройки → группа → домен**. Домен не переопределяет ничего из расписания и уведомлений.

| Параметр | Где задаётся | Правило разрешения |
|---|---|---|
| Период проверки | общие, группа | значение группы, если задано; иначе общее |
| Порог актуальности | общие, группа | значение группы, если задано; иначе общее |
| Режим уведомлений | общие, группа | значение группы, если задано; иначе общее |
| Сообщать о возврате в норму | общие, группа | значение группы, если задано; иначе общее |
| Интервал напоминаний | общие, группа | значение группы, если задано; иначе общее |
| Разрешённые адреса и подсети | домен | только домен, наследования нет |
| Комментарий | домен, группа | см. 8.4 — правило подстановки в уведомление |
| Типы записей | домен | только домен |

Домен без группы берёт все наследуемые параметры из общих настроек.

Интерфейс обязан показывать происхождение значения: «общая», «от группы», «своё». Рядом со «своим» значением у группы — кнопка возврата к значению по умолчанию.

## 6. Алгоритм проверки

### 6.1 Резолв

1. Выбрать домены, у которых наступило время проверки (см. 11.1).
2. Для домена выполнить запрос типов записей, отмеченных у него флагами.
3. DNS-серверы опрашиваются **по порядку** из общего списка, до первого успешного ответа. Локальный резолвер прописывается в этот же список как обычная строка.
4. Таймаут на сервер — настраиваемая константа (по умолчанию 3 секунды).
5. Пустой ответ (`NOERROR` без записей) и `NXDOMAIN` — это **не ошибка сети**, а результат: домен не резолвится. Переход к следующему серверу в этом случае не выполняется.
6. Сетевая ошибка или таймаут — переход к следующему серверу. Если все серверы недоступны, проверка считается несостоявшейся: реестр и статусы **не меняются**, событие не порождается, фиксируется техническая ошибка.

Отличать «домен не резолвится» от «мы не смогли спросить» обязательно. Второе не должно порождать уведомлений.

### 6.2 Определение актуального набора

Пусть `T` — момент проверки, `W` — порог актуальности домена (через группу).

```
Актуальный набор = { ip из реестра домена : ip.последнее_обнаружение >= T - W }
```

Адреса из текущего ответа записываются в реестр (создаются или обновляют `последнее_обнаружение = T`) **до** вычисления набора.

### 6.3 Проверка вхождения в белый список

Адрес `ip` считается решённым, если существует запись списка `e`, такая что:

- `e` — отдельный адрес и `e == ip`, либо
- `e` — подсеть и `ip` принадлежит `e`.

Правила:

- Отдельный адрес эквивалентен подсети с полной маской (`/32` для IPv4, `/128` для IPv6). Можно так и хранить, но в интерфейсе показывать как ввёл пользователь.
- Сравнение выполняется **в пределах одного семейства адресов**. IPv4-адрес не сравнивается с IPv6-записью и наоборот.
- Список проверяется целиком; какая именно запись совпала — сохраняется для показа в интерфейсе.

Формулировка причины совпадения в интерфейсе зависит от вида записи:

- запись с маской → «входит в 10.20.0.0/22»;
- запись без маски → «точное совпадение с 10.20.3.7».

Вариант «входит в 10.20.3.7» не использовать: одиночный адрес ни во что не входит, и такая формулировка сбивает с толку.

### 6.4 Статус адреса

Статус вычисляется, а не хранится. Приоритет сверху вниз:

1. **Не актуален** — адрес есть в реестре, но `последнее_обнаружение < T - W`. Вопрос о вхождении в список для него не задаётся.
2. **Не решён** — адрес актуален и не совпал ни с одной записью списка.
3. **Решён** — адрес актуален и совпал.

Статус самого домена — производная от статусов его адресов:

- есть хотя бы один нерешённый → домен в состоянии расхождения;
- иначе, если домен не резолвится N проверок подряд → домен в состоянии ошибки резолва;
- иначе норма.

## 7. События

Событие — факт в журнале. Отправляется ли по нему уведомление, решает раздел 8.

### 7.1 Список типов

| Тип | Когда возникает |
|---|---|
| `ADDRESS_APPEARED` | Адрес присутствует в ответе и до этой проверки **не входил** в актуальный набор (его не было в реестре либо он был неактуален). |
| `ADDRESS_GONE` | Адрес входил в актуальный набор, и в момент этой проверки `последнее_обнаружение` пересёк границу `T - W`. |
| `NOT_ALLOWED` | В актуальном наборе появился адрес со статусом «Не решён», которого в прошлой проверке в этом статусе не было. |
| `BACK_TO_NORMAL` | У домена был открытый инцидент, и в актуальном наборе не осталось нерешённых адресов. |
| `RESOLVE_FAILED` | Домен не резолвится N проверок подряд (N из общих настроек). Повторно не порождается, пока не было успешного резолва. |
| `RESOLVE_RECOVERED` | Домен снова резолвится после `RESOLVE_FAILED`. |
| `WATCH_STARTED` | Установлен базовый уровень домена. См. 7.4. |

### 7.2 Почему нужен порог актуальности

Это ключевая логика, не упрощать.

Если DNS перебирает адреса по кругу, в каждом отдельном ответе присутствует лишь часть адресов. Без порога каждая такая перестановка выглядела бы как «один адрес появился, другой пропал», и сервис слал бы уведомления непрерывно.

Порог решает это: адрес считается частью набора, пока отдавался хотя бы раз за последние `W`. Перестановки внутри `W` событиями не являются. `ADDRESS_GONE` возникает единственный раз — в момент пересечения границы.

Валидация: порог актуальности должен быть **заметно больше** периода проверки, иначе за него не успевает пройти полный круг адресов. См. открытый вопрос 13.1.

### 7.3 Инциденты и дедупликация

`NOT_ALLOWED` не должен повторяться на каждой проверке, пока проблема держится.

- Если у домена **нет** открытого инцидента и появился нерешённый адрес — открыть инцидент, породить `NOT_ALLOWED`.
- Если инцидент **открыт** и появился **ещё один** нерешённый адрес — породить `NOT_ALLOWED` с новым адресом, инцидент не дублировать.
- Если инцидент открыт и нерешённых адресов не осталось — закрыть инцидент, породить `BACK_TO_NORMAL` с длительностью инцидента.

Уведомление о `BACK_TO_NORMAL` отправляется **ответом** на сообщение, которым открывался инцидент. Для этого идентификатор исходного сообщения хранится в инциденте.

### 7.4 Базовая проверка

**Проблема.** Правило `ADDRESS_APPEARED` из 7.1 гласит: событие возникает для адреса, которого не было в актуальном наборе. При первой в жизни проверке в наборе нет ничего, поэтому новыми оказываются **все** адреса. Импорт 200 доменов с включённым флагом «проверить сразу» породит более 200 событий и столько же сообщений. Инструмент будет отключён в первый же день.

**Решение.** Вводится понятие **базовой проверки** — проверки, которая устанавливает отправную точку и не порождает событий изменения.

Проверка считается базовой в трёх случаях:

1. Первая успешная проверка домена после его создания.
2. Первая успешная проверка после включения ранее выключенного домена, если пауза была дольше порога актуальности.
3. Первая успешная проверка после простоя самого сервиса, если с момента последней успешной проверки **этого домена** прошло больше порога актуальности.

Третий случай в исходной постановке отсутствовал, но относится к тому же классу и опаснее остальных: после суточного простоя сервиса актуальный набор каждого домена окажется просроченным, и обычная логика объявит новыми все адреса всех доменов сразу.

**Поведение на базовой проверке:**

- Адреса записываются в реестр, актуальный набор формируется обычным образом.
- События `ADDRESS_APPEARED` и `ADDRESS_GONE` **не порождаются**.
- Порождается ровно одно событие `WATCH_STARTED` с числом зафиксированных адресов: «наблюдение начато, зафиксировано N адресов» либо «наблюдение возобновлено» для случаев 2 и 3.
- Уведомление по `WATCH_STARTED` не отправляется.

**Отдельно о нерешённых адресах на базовой проверке.** Вхождение в белый список — критерий абсолютный, а не относительный: он не зависит от того, что было раньше. Если домен с первого же ответа указывает вне списка, это настоящая проблема, и глушить её нельзя.

Поэтому:

- Инцидент открывается как обычно, статус виден в интерфейсе немедленно.
- Событие `NOT_ALLOWED` порождается.
- Уведомление по нему отправляется **через механизм слияния** (8.6), то есть при массовом импорте уходит одно сводное сообщение вида «12 доменов из 200 сразу указывают вне списка», а не двенадцать отдельных.
- В тексте `WATCH_STARTED` дополнительно указывается «из них M не решены».

## 8. Уведомления

### 8.1 Режимы

Режим задаётся в группе или берётся из общих настроек. Три значения:

| Режим | Какие события порождают уведомление |
|---|---|
| Не уведомлять | никакие |
| При изменении адресов | `ADDRESS_APPEARED`, `ADDRESS_GONE` |
| При выходе из разрешённых | `NOT_ALLOWED` |

`BACK_TO_NORMAL` уведомляет дополнительно, если включён флаг «сообщать о возврате в норму», и только в режимах, отличных от «Не уведомлять».

`RESOLVE_FAILED` уведомляет во всех режимах, кроме «Не уведомлять». Это техническая неисправность, а не изменение конфигурации.

### 8.2 Ловушка, которую обязан отлавливать интерфейс

Домен с **пустым** белым списком в режиме «При выходе из разрешённых» не пришлёт уведомление **никогда**. Логика верна, но пользователь этого не ожидает.

Требование: в списке доменов такие домены помечаются, есть фильтр «Без разрешённых», и при сохранении домена с пустым списком в такой группе показывается предупреждение.

### 8.3 Каналы доставки

В первой версии обязателен **Telegram**. Архитектуру каналов сделать расширяемой: почта и вебхук предусмотрены, реализация почты может быть отложена.

**Разграничение подключения и адресата.** Для каждого канала параметры делятся надвое:

- **Подключение** — то, что даёт доступ к чужой инфраструктуре: адрес почтового сервера и учётные данные к нему. Задаётся в окружении, из интерфейса не меняется. Администратор приложения не должен получать возможность направить исходящую почту через свой сервер.
- **Адресат** — кому отправлять: идентификатор чата Telegram, перечень почтовых адресов, адрес вебхука. Это решение о работе продукта, оно остаётся в интерфейсе.

Состояние канала («Настроен» или «Не настроен») показывается в интерфейсе только для чтения, с именами переменных окружения. Кнопка «Отправить тестовое сообщение» допустима: это проверка, а не изменение настройки.

Требования к доставке:

- Очередь с повторами при ошибке отправки. Экспоненциальная задержка, конечное число попыток.
- Результат доставки фиксируется в журнале и виден рядом с событием.
- Недоступность канала не должна останавливать проверки.

### 8.4 Состав сообщения

Порядок строк фиксирован. Сначала факты, потом что делать, потом ссылка.

1. Заголовок — тип события.
2. Имя домена.
3. Изменившиеся адреса со знаком: появившийся, пропавший, нерешённый.
4. Полный текущий набор адресов (отключаемо настройкой).
5. Название группы.
6. Комментарий (отключаемо настройкой).
7. Ссылка на карточку домена (отключаемо настройкой).

Правило подстановки комментария: берётся комментарий домена; если он пуст — комментарий группы; если пуст и он — строка не выводится.

Ограничения Telegram:

- Предел сообщения 4096 символов. При переполнении **сокращается список адресов** (первые 8 и «и ещё N»), комментарий не сокращается.
- Разметка — ограниченный HTML или MarkdownV2. Цвета нет, таблиц нет: смысл несут порядок строк и моноширинный шрифт для адресов.
- Специальные символы экранируются.

### 8.5 Повторные напоминания по открытому инциденту

Одно сообщение в три часа ночи в шумном чате теряется, и заявленная ценность «узнать раньше всех» исчезает. Поэтому по открытому инциденту уведомление повторяется.

- Настройка **интервал напоминаний** задаётся в группе или берётся из общих настроек. Значения: не напоминать / 1 час / 6 часов / 24 часа. По умолчанию 6 часов.
- Напоминание отправляется **ответом в ту же ветку**, что и сообщение об открытии инцидента.
- Содержание: возраст инцидента, текущий список нерешённых адресов (он мог измениться с момента открытия), ссылка. Комментарий домена в напоминании не повторяется — он уже был в первом сообщении.
- Отсчёт интервала ведётся от последнего отправленного сообщения по этому инциденту, а не от момента его открытия.
- Если за интервал состав нерешённых адресов изменился, уходит обычное `NOT_ALLOWED` о новом адресе, и оно **засчитывается за напоминание**. Два сообщения подряд не отправляются.
- Напоминания прекращаются при закрытии инцидента. См. также открытый вопрос 13.7 об откладывании.

### 8.6 Слияние массовых событий

Защита от лавины в любых сценариях, а не только при импорте.

- Если в пределах **окна слияния** (по умолчанию 60 секунд) на один канал доставки приходится больше **порога слияния** событий одного типа (по умолчанию 5), они отправляются одним сводным сообщением. Накопитель окна живёт в Redis (11.11).
- Сводка содержит: тип события, число затронутых доменов, перечисление до 10 имён, «и ещё N», ссылку на журнал с уже применённым фильтром.
- События при этом записываются в журнал по отдельности. Сливается только доставка.
- Инциденты открываются и закрываются по обычным правилам, слияние на них не влияет.
- Правило срабатывает при массовом импорте, включении группы целиком, изменении белого списка сразу у многих доменов и при восстановлении сервиса после простоя.

## 9. Реестр адресов

### 9.1 Назначение

Ответить на вопрос «насколько этот адрес актуален для этого домена». Для этого хранятся момент первого и последнего обнаружения каждой пары «домен + адрес».

Реестр не удаляется вместе с журналом: срок хранения задаётся отдельно и по умолчанию бессрочный.

### 9.2 График

График показывает **след из отметок по времени**, а не сплошную полосу от первой даты до последней. Это принципиально: сплошная полоса скрывает пропуски и вынуждает объяснять словами то, что должно быть видно.

Правила отрисовки:

- Ось времени по умолчанию охватывает **весь срок наблюдения за доменом**. Тогда след любого адреса гарантированно попадает в поле зрения, и не нужны пометки «интервал начался левее».
- Время делится на корзины. Корзина закрашена, если адрес отдавался хотя бы в одном ответе за её период.
- **Число корзин определяется шириной элемента, а не календарём.** Ширина одной отметки не менее 4–5 пикселей. Количество корзин = ширина / 5, ограниченное сверху числом периодов в диапазоне. При изменении размера окна график перестраивается.
- Текущая цена деления подписывается рядом: «110 суток · одна отметка — 2 суток».
- Всплывающая подсказка на отметке показывает её период и был ли адрес в ответе. При укрупнённой корзине это единственный способ узнать точную дату.
- Цвет отметки соответствует **текущему** статусу адреса: зелёный — решён, красный — не решён, серый — не актуален. Незакрашенная отметка означает, что в этот период адрес не отдавался.

Предел, который нужно принять: при узком экране корзина укрупняется и суточные пропуски перестают быть видны. Это устраняется переключателем масштаба (24 часа / 7 дней / 30 дней / всё наблюдение), а не уплотнением отметок.

## 10. Ввод и валидация данных

### 10.1 Доменные имена

- Приводятся к нижнему регистру, конечная точка отбрасывается.
- Не-ASCII имена преобразуются в punycode. Если преобразование невозможно — ошибка ввода с внятным текстом.
- Дубликаты внутри установки не допускаются.

### 10.2 Записи белого списка

- Принимается отдельный адрес (`10.20.3.7`) или подсеть (`10.20.0.0/22`), IPv4 и IPv6.
- Октеты и длина маски валидируются. `10.20.999.0/24` — ошибка с указанием причины.
- Адрес подсети с ненулевой хостовой частью (`10.20.1.5/24`) — либо нормализуется к `10.20.1.0/24` с показом изменения, либо отклоняется. См. открытый вопрос 13.3.

**Требования к полю ввода.** Белый список — самое частое место ввода во всём продукте, и текстовое поле без обратной связи здесь недопустимо.

- Валидация построчная и немедленная: ошибочная строка подсвечивается, рядом с ней показывается причина простым языком («999 — недопустимый октет»), а не код ошибки.
- Сохранение блокируется, пока есть хотя бы одна ошибочная строка. Корректные строки при этом не теряются.
- Нормализованная запись показывается до сохранения, если ввод был изменён.

Предупреждения, которые **не блокируют** сохранение, но показываются:

- дубликат записи в пределах списка;
- запись, полностью покрытая другой (`10.20.3.7` внутри `10.20.0.0/22`) — вероятно, лишняя;
- запись семейства адресов, которое у домена не запрашивается (запись IPv6 при выключенном типе AAAA).

### 10.3 Импорт списком

Двухшаговый: вставка → разбор → подтверждение. Импорт **не выполняется вслепую**.

Формат строки: `домен; разрешённые записи через пробел; комментарий`. Второе и третье поля необязательны.

Источники: вставка текста и загрузка файла `.txt` / `.csv`.

Шаг разбора обязан показать:

- сводку «сколько добавим, сколько уже есть, сколько с ошибкой»;
- построчную таблицу с результатом разбора и причиной ошибки;
- домены без разрешённых записей — принимаются, но помечаются предупреждением о том, что следить получится только за изменением.

Поведение при подтверждении:

- Строки с ошибками **остаются в поле ввода**, чтобы их можно было исправить и повторить. Не выбрасывать молча.
- Флаг «Обновить домены, которые уже есть» — **выключен по умолчанию**. Перезапись чужих настроек не должна происходить сама собой.
- Флаг «Проверить домены сразу после импорта» — включён по умолчанию. Первый ответ становится отправной точкой для сравнений.

### 10.4 Перенос домена в другую группу

Перенос молча меняет расписание и режим уведомлений. Интерфейс обязан показать сводку «что изменится» **до** подтверждения:

- период проверки: было → станет;
- режим уведомлений: было → станет;
- явное перечисление того, что не изменится: разрешённые адреса, комментарий, реестр.

Если у домена **сейчас открыт инцидент**, а целевая группа работает в режиме, который такие события не отслеживает, — показать отдельное предупреждение.

Выбор группы везде выполняется полем с поиском, а не простым списком: групп может быть много. В поле показывается число доменов в группе; при отсутствии совпадений предлагается создать группу с введённым названием.

## 11. Нефункциональные требования

### 11.1 Планировщик

- Следующая проверка домена = момент последней проверки + период его группы.
- Проверки разных доменов **разносятся во времени** случайным смещением, иначе все домены с периодом 5 минут выстроятся в один пик.
- Ограничение параллелизма резолвов настраивается.
- Отключённый домен не проверяется, но его реестр сохраняется.
- Перезапуск сервиса не должен вызывать одновременный резолв всего списка.
- При запуске нескольких экземпляров сервиса один домен не должен резолвиться двумя из них одновременно. Взаимное исключение — ключом в Redis (11.11).

### 11.2 Масштаб

Ориентир первой версии: до 1000 доменов, минимальный период 1 минута. Архитектура не должна упираться в этот потолок, но оптимизация под большее не требуется.

### 11.3 Хранение

- Журнал событий: срок настраивается, по умолчанию 90 дней, старое удаляется.
- Реестр адресов: срок настраивается, по умолчанию бессрочно.
- Удаление домена удаляет его реестр и события. Удаление группы **не удаляет** её домены — они переходят в состояние «без группы» и начинают наследовать общие настройки. Это действие требует подтверждения с указанием числа затронутых доменов.

### 11.4 Интерфейс

- Язык русский. Термины строго из глоссария.
- Адреса, домены и записи CIDR — всегда моноширинным шрифтом.
- Адаптация под телефон обязательна. Основной мобильный сценарий: переход по ссылке из уведомления на карточку домена ночью. Таблицы на узком экране превращаются в карточки, горизонтальной прокрутки таблиц быть не должно.
- Линейка подсети: при наложении меток они склеиваются в одну с числом адресов, позиция при этом остаётся честной. Клик по склеенной метке открывает увеличенный фрагмент диапазона, на котором адреса расходятся. Подписи не раздвигаются в ущерб точности позиции.

### 11.5 Колонка «История» в списке доменов

Компактная лента из 20 отметок. **Ось — последовательность проверок, а не время.** Это отличает её от следа в реестре адресов, где ось временная. Смешивать их нельзя, и в подсказке к колонке это различие должно быть названо.

- Одна отметка — одна проверка домена, слева направо от старых к новым, ровно 20 последних.
- Цвет отметки — исход проверки: серый — норма; янтарный — набор адресов изменился; красный — есть нерешённый адрес; фиолетовый — ошибка резолва.
- Пустая отметка означает, что проверки не было: домен моложе 20 проверок либо был выключен. Пустая отметка **не** означает «всё хорошо».
- Наведение показывает время проверки и её исход.

### 11.6 Ручная проверка

Глобальная кнопка «проверить все домены» **не реализуется**: при тысяче доменов она создаёт пик нагрузки, который невозможно отменить, и не имеет осмысленного применения.

Вместо неё:

- «Проверить сейчас» на карточке домена. Кулдаун 30 секунд, реализуется ключом в Redis (11.11).
- «Проверить домены группы» на экране группы. Кулдаун 60 секунд, ограничение параллелизма то же, что у планировщика.
- Если в группе больше 200 доменов, запуск требует подтверждения с указанием их числа.

Ручная проверка — настоящая проверка: она порождает события на общих основаниях и сдвигает время следующей плановой проверки, чтобы не удваивать нагрузку.

### 11.7 Выгрузка журнала

- Формат CSV, кодировка UTF-8 с BOM, разделитель — точка с запятой. Это сочетание открывается в Excel без шаманства с импортом.
- Выгружается **текущая выборка** с применёнными фильтрами и периодом, а не весь журнал.
- Колонки: момент события в ISO 8601, домен, группа, тип события, затронутые адреса, режим уведомлений на момент события, канал доставки, результат доставки.
- Ограничение 100 000 строк. При превышении выгрузка не выполняется, предлагается сузить период.

### 11.8 Что показывать на карточке домена

Блок унаследованных настроек обязан включать **все** параметры, от которых зависит то, что человек видит на этой же странице:

- группа;
- период проверки;
- порог актуальности — от него напрямую зависит статус «Не актуален», который тут же показан в реестре;
- режим уведомлений;
- интервал напоминаний.

Без порога актуальности статус «Не актуален» выглядит как решение, принятое неизвестно на каком основании.

### 11.9 Блок «Открытые расхождения» на обзоре

Счётчик «Не решены: 1» не заменяет списка: он не говорит ни какой домен, ни как давно.

- Список открытых инцидентов, отсортированный по возрасту по убыванию.
- Для каждого: имя домена, нерешённые адреса, **возраст инцидента** в читаемом виде («держится 3 ч 12 мин»), время последнего отправленного напоминания, переход к карточке.
- Если открытых инцидентов нет — явная строка «Открытых расхождений нет» с датой последнего закрытого, а не пустое место.

### 11.10 Настройки окружения

Граница между `.env` и настройками в интерфейсе проводится по одному признаку.

**В `.env`** — то, что описывает установку и уровень безопасности: подключения, секреты, ограничения ресурсов, включение второго фактора. Изменение требует доступа к серверу и перезапуска. Администратор приложения изменить это не может.

**В интерфейсе** — то, что описывает поведение продукта: периоды, пороги, режимы уведомлений, каналы доставки. Изменение доступно администратору и не требует перезапуска.

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `DATABASE_URL` | подключение к БД | обязательна |
| `REDIS_URL` | подключение к Redis | обязательна |
| `REDIS_DB_STATE` | номер логической базы под рабочее состояние | `0` |
| `REDIS_DB_CACHE` | номер логической базы под кэш | `1` |
| `APP_BASE_URL` | адрес установки, подставляется в ссылки в уведомлениях и приглашениях | обязательна |
| `SESSION_SECRET` | подпись сессий | обязательна |
| `AUTH_2FA_ENABLED` | второй фактор для всех участников | `false` |
| `DNS_TIMEOUT_MS` | таймаут запроса к одному DNS-серверу | `3000` |
| `RESOLVE_CONCURRENCY` | предел одновременных резолвов | `20` |
| `SMTP_HOST` | адрес почтового сервера. Пустое значение выключает отправку писем | пусто |
| `SMTP_PORT` | порт почтового сервера | `587` |
| `SMTP_USER` | учётная запись для отправки | пусто |
| `SMTP_PASSWORD` | пароль учётной записи | пусто |
| `SMTP_FROM` | адрес отправителя | пусто |
| `SMTP_TLS` | режим шифрования: `starttls`, `tls`, `none` | `starttls` |
| `SENTRY_DSN` | адрес проекта Sentry. Пустое значение выключает отправку | пусто |
| `SENTRY_ENVIRONMENT` | метка окружения в Sentry | `production` |
| `SENTRY_TRACES_SAMPLE_RATE` | доля запросов для отслеживания производительности | `0` |

`SENTRY_DSN` и `SMTP_HOST` — переменные, пустое значение которых является нормальным режимом работы, а не ошибкой конфигурации. Без Sentry приложение работает без отправки ошибок, без SMTP — без отправки писем.

Если `SMTP_HOST` задан, остальные переменные группы проверяются на непротиворечивость при старте: заданный `SMTP_USER` без `SMTP_PASSWORD` или отсутствие `SMTP_FROM` — ошибка конфигурации, приложение не стартует. Доступность самого сервера при старте не проверяется: сетевая проба на старте делает запуск зависимым от чужой инфраструктуры.

Приложение обязано **падать при старте** с внятным сообщением, если обязательная переменная не задана или не проходит проверку формата. Молчаливый запуск со значением по умолчанию вместо `APP_BASE_URL` даст рабочий сервис, рассылающий уведомления с нерабочими ссылками, и обнаружится это нескоро.

### 11.11 Использование Redis

**Redis — обязательная часть инфраструктуры.** Он должен быть доступен всегда. Его недоступность — авария, а не режим пониженной функциональности. Поведение при аварии описано в 11.13.

**Первое правило: Redis не является источником истины.** Потеря его содержимого не должна приводить к потере доменов, событий, реестра адресов или участников. Всё, что обязано пережить перезапуск, лежит в БД. Из этого не следует, что потеря безобидна: она означает сброс счётчиков, кулдаунов и блокировок и требует разбора.

**Второе правило: ключ без срока жизни запрещён.** Каждый ключ создаётся с `TTL`, причём срок должен быть осмысленным — производным от логического окна, а не «на всякий случай сутки». Ключ, который не исчезнет сам, однажды накопится и переживёт причину своего появления.

| Ключ | Что хранит | Срок жизни |
|---|---|---|
| `auth:fail:{хеш логина}:{ip}` | счётчик неудачных попыток входа | окно счёта, 15 минут |
| `auth:lock:{хеш логина}:{ip}` | признак блокировки входа | срок блокировки, 15 минут |
| `auth:otp:{id участника}:{шаг}` | отметка об использованном коде TOTP | 90 секунд, два шага кода |
| `check:cooldown:domain:{id}` | кулдаун ручной проверки домена | 30 секунд |
| `check:cooldown:group:{id}` | кулдаун ручной проверки группы | 60 секунд |
| `sched:lock:domain:{id}` | блокировка домена на время проверки, чтобы два экземпляра сервиса не резолвили его одновременно | таймаут проверки с запасом, 30 секунд |
| `notify:merge:{канал}:{тип события}` | накопитель окна слияния массовых событий (8.6) | окно слияния с запасом, 90 секунд |

Это **рабочее состояние**. Оно живёт в логической базе `REDIS_DB_STATE`, и политика вытеснения для неё — `noeviction`. Вытеснение блокировки планировщика под нагрузкой означало бы, что два экземпляра сервиса резолвят один домен и дублируют уведомления.

Уточнения по реализации:

- **Логин в ключе хешируется.** Иначе содержимое Redis становится перечнем почтовых адресов участников в открытом виде.
- **Срок жизни счётчика ставится только при первом увеличении**, окно фиксированное. Если продлевать срок при каждой неудаче, редкие опечатки легитимного пользователя будут накапливаться месяцами и однажды приведут к блокировке на ровном месте.
- **Блокировка снимается сама** истечением срока ключа. Отдельного задания по расписанию, снимающего блокировки, быть не должно.
- **Блокировка планировщика освобождается явно** по завершении проверки, а срок жизни служит страховкой на случай падения экземпляра посреди работы.

### 11.12 Кэширование

Кэш живёт в отдельной логической базе `REDIS_DB_CACHE` с политикой вытеснения `volatile-lru`. Разделение обязательно: кэш можно сбрасывать целиком в любой момент, рабочее состояние — нельзя.

Ключи кэша начинаются с префикса `cache:`. Сброс по шаблону `cache:*` должен быть безопасной операцией под нагрузкой.

| Ключ | Что хранит | Срок жизни | Как обновляется |
|---|---|---|---|
| `cache:settings:domain:{id}:v{версия}` | разрешённые по цепочке наследования период, порог актуальности, режим уведомлений, интервал напоминаний | 1 час | версия в ключе меняется при правке общих настроек, группы или домена |
| `cache:allowlist:domain:{id}:v{версия}` | разобранный белый список в виде диапазонов, готовых к проверке вхождения | 1 час | версия меняется при сохранении списка |
| `cache:trace:domain:{id}:{размер корзины}` | агрегированный по корзинам след для графика реестра | 5 минут | по сроку |
| `cache:view:overview` | счётчики и список открытых расхождений на обзоре | 15 секунд | по сроку |
| `cache:view:domains:{хеш фильтра}` | страница списка доменов со статусами | 30 секунд | по сроку |
| `cache:user:{id}` | роль и признак активности участника | 30 секунд | удаляется немедленно при смене роли или отключении участника |

Два разных подхода к обновлению, и путать их нельзя.

**Только по сроку** обновляются представления: обзор, список доменов, график. Отставание на секунды здесь безвредно, а явная инвалидация каждого представления при каждом событии обошлась бы дороже пользы.

**По версии в ключе** обновляются настройки и белый список. Здесь отставание опасно. Человек, который добавил подсеть, чтобы прекратить ложную тревогу, обязан увидеть результат на следующей же проверке. Если список останется в кэше ещё час, он решит, что сервис сломан, и будет прав.

Версия в ключе предпочтительнее удаления ключа: при нескольких экземплярах сервиса удаление подвержено гонке, а смена версии просто делает старый ключ недостижимым, и он уходит сам по сроку.

**Роль участника** кэшируется не дольше 30 секунд и удаляется немедленно при отключении участника или смене роли. Отозванный доступ не должен переживать своё отзывание.

**Не кэшируются никогда:** результат проверки вхождения конкретного адреса, содержимое журнала событий, реестр адресов как таковой, данные аутентификации.

### 11.13 Поведение при недоступном Redis

Недоступность Redis — авария. Приложение не переходит в режим пониженной функциональности и не пытается работать «как получится».

Что обязано произойти:

- Проба работоспособности (`healthcheck`) переходит в нездоровое состояние и называет причину.
- Интерфейс и API отвечают `503` со страницей, прямо называющей отказавший компонент. Не «что-то пошло не так».
- Проверки доменов останавливаются. Без взаимного исключения несколько экземпляров сервиса задублируют уведомления, а без кэша настроек каждый резолв пойдёт в БД за цепочкой наследования.
- Факт остановки записывается в журнал и, если Sentry подключён, отправляется туда как отказ инфраструктуры (11.14).

**Уведомление об аварии не должно зависеть от Redis.** Сообщение о том, что сервис перестал проверять домены, отправляется в канал доставки напрямую, минуя окно слияния и очередь, если та тоже опирается на Redis. Компонент, сообщающий об отказе, не может зависеть от отказавшего.

Это главное требование раздела. Инструмент мониторинга, который молча перестал мониторить, опаснее отсутствия инструмента: люди продолжают считать, что за доменами следят.

**После восстановления.** Если простой был дольше порога актуальности, проверки выполняются как базовые по правилу 7.4, случай 3. Лавины уведомлений о «новых» адресах быть не должно.

### 11.14 Отправка ошибок в Sentry

Подключение необязательное. При пустом `SENTRY_DSN` приложение работает как обычно, ничего никуда не отправляет и не пишет в журнал попыток отправки. Заданный DSN неверного формата — ошибка конфигурации, приложение не стартует.

**Sentry никогда не влияет на работу приложения.** Отправка асинхронная, её неудача проглатывается. Это принципиальное отличие от Redis: тот обязателен и его отсутствие — авария, Sentry же необязателен и его отсутствие не значит ничего.

#### Что отправляется

- Необработанные исключения в любом слое.
- Отказы инфраструктуры: недоступность Redis, БД, почтового сервера.
- Неудача доставки уведомления после исчерпания всех повторов.
- Падение планировщика или отдельного обработчика проверок.
- Ошибка применения миграций.

#### Что не отправляется никогда

Это главный раздел. Продукт про мониторинг устроен так, что «отказов» в нём много, и почти все они не являются ошибками приложения.

- **Домен не резолвится** (`NXDOMAIN`, пустой ответ). Это результат наблюдения, ради которого сервис и существует. Место таким записям — журнал событий.
- **Адрес вне белого списка.** Тем более: это и есть полезная работа продукта.
- **Таймаут одного DNS-сервера** при наличии следующего в списке. Штатная ситуация, ради которой список и упорядочен.
- **Ошибка ввода пользователя**: неверный CIDR, кириллический домен в импорте, дубликат.
- **Неудачная попытка входа, блокировка, просроченное приглашение.**

Если отправлять это в Sentry, за сутки он наберёт тысячи событий, и разработчики перестанут туда смотреть ровно тогда, когда там появится настоящая ошибка.

#### Группировка

Отпечаток события формируется **по причине, а не по объекту**.

Если при обходе отказали все DNS-серверы, пятьсот доменов дадут пятьсот исключений. В Sentry это должно быть **одно** событие с числом затронутых доменов в контексте, а не пятьсот отдельных. Иначе квота проекта выгорает за минуты, а картина отказа не становится понятнее.

То же правило действует при недоступности Redis и БД: группировка по отказавшему компоненту.

#### Контекст события

К каждому событию прикладываются метки, позволяющие связать ошибку с объектом предметной области: идентификаторы домена, группы, проверки и инцидента, а также идентификатор обхода — чтобы все ошибки одного цикла проверок нашлись вместе.

Версия сборки указывается как релиз, иначе невозможно понять, какое развёртывание сломало работу.

#### Что вырезается перед отправкой

- Токен бота Telegram, `SMTP_PASSWORD`, `SESSION_SECRET` и любые значения из `.env`, содержащие пароли: строки подключения к БД и Redis.
- Хеши паролей, токены приглашений, значения сессионных cookie.
- Тела запросов к обработчикам входа и смены пароля целиком.
- Участник обозначается идентификатором, а не почтовым адресом.

Белые списки, имена доменов и IP-адреса вырезать не нужно: без них ошибка нечитаема, а секретом они не являются.

#### Разграничение с уведомлениями

Sentry — для разработчиков, Telegram — для дежурных. Смешивать нельзя: трассировка стека в чате дежурной смены бесполезна, а расхождение адресов домена не является ошибкой кода.

Единственное пересечение — авария инфраструктуры вроде недоступности Redis. Она уходит **в оба канала**: дежурным, потому что сервис перестал следить за доменами, и в Sentry, потому что разработчикам нужна причина.

## 12. Чего делать не надо

Эти решения были рассмотрены и отклонены. Не реализовывать и не предлагать заново без отдельного запроса.

- **Чёрный список адресов.** Только белый.
- **Период проверки у отдельного домена.** Только у группы. Обходной путь для единичного случая — группа из одного домена.
- **Отдельный механизм подавления «дребезга» помимо порога актуальности.** Порог его уже решает.
- **Отдельная сущность «известные адреса».** Объединена с белым списком: отдельный адрес — это запись с полной маской.
- **Наследование белого списка от группы или общих настроек.** Список принадлежит только домену.
- **Настройка DNS-серверов на уровне группы.** Список общий; локальный резолвер вписывается в него строкой.
- **Отрисовка порога актуальности на графике.** Порог — правило для уведомлений, а не элемент визуализации. Обрыв следа виден и без него.
- **Пометки вида «интервал выходит за границу показанного отрезка».** Устраняются правильным масштабом по умолчанию, а не подписью.
- **Глобальная кнопка «Проверить всё сейчас».** Заменена проверкой домена и проверкой группы с кулдауном, см. 11.6.
- **Показ уведомлений по первой проверке домена.** См. 7.4, базовая проверка тихая.
- **Переключатель второго фактора в интерфейсе.** Только переменная окружения, см. 3 и 11.10.
- **Смена роли выпадающим списком прямо в таблице участников.** Только через окно редактирования.
- **Удаление участника, который уже входил.** Только отключение, иначе журнал теряет авторство.
- **Настройка почтового сервера в интерфейсе.** Адрес, порт и учётные данные — только в окружении, см. 8.3 и 11.10. Кнопки «Подключить почту» быть не должно.
- **Таблица в БД под счётчик неудачных входов.** Только Redis со сроком жизни, см. 11.11.
- **Ключи Redis без срока жизни.** Считать ошибкой при проверке кода.
- **Общее пространство ключей для кэша и рабочего состояния.** Разные логические базы и разные политики вытеснения, см. 11.11 и 11.12.
- **Работа при недоступном Redis в урезанном режиме.** Это авария, см. 11.13.
- **Долгое кэширование роли участника.** Не дольше 30 секунд, с немедленным удалением при отзыве доступа.
- **Отправка событий предметной области в Sentry.** `NXDOMAIN`, адрес вне списка, ошибка ввода и неудачный вход туда не идут, см. 11.14.
- **Зависимость работы приложения от доступности Sentry.** Отправка асинхронная, её неудача игнорируется.
- **Отправка в Sentry секретов и почтовых адресов участников.** См. перечень вырезаемого в 11.14.

## 13. Открытые вопросы

Закрыть до реализации соответствующего раздела.

**13.1. Соотношение периода проверки и порога актуальности.**
Комбинация «период 6 часов, порог 1 час» ломает логику: за порог не успевает пройти круг адресов, и половина набора ложно уйдёт в «Не актуален». Варианты: запретить сохранение такой комбинации; автоматически поднимать порог; ограничиться предупреждением. Нужно выбрать.

**13.2. Скорость закрытия инцидента.**
Если `BACK_TO_NORMAL` наступает только когда нерешённый адрес выпал из актуального набора, то при пороге 24 часа сообщение о возврате в норму придёт через сутки после фактического исправления. Это слишком поздно.
Рекомендация: ввести **отдельный, короткий критерий закрытия** — нерешённый адрес отсутствует в K последних подряд ответах (K по умолчанию 3), независимо от порога актуальности. Требует подтверждения.

**13.3. Нормализация подсети с ненулевой хостовой частью.**
`10.20.1.5/24` — молча нормализовать к `10.20.1.0/24`, нормализовать с показом изменения, или отклонять как ошибку ввода.

**13.4. Адрес другого семейства при непустом списке.**
Домен отдаёт AAAA-запись, а в белом списке только IPv4. Формально адрес не решён, и уведомление уйдёт. Это может быть и реальной проблемой, и просто незаполненным списком. Нужно решить: считать нерешённым (текущее правило), либо игнорировать семейство, для которого нет ни одной записи, показывая предупреждение в интерфейсе.

**13.5. Устаревшие записи белого списка.**
Разрешённый адрес, который не отдаётся год, продолжает висеть в списке и однажды может «разрешить» то, что уже не должно быть разрешено. Нужен ли критерий устаревания и подсветка таких записей в реестре.

**13.6. Откладывание напоминаний.**
Нужна ли дежурному кнопка «отложить напоминания на N часов» по открытому инциденту. Без неё человек, уже взявший проблему в работу, продолжает получать сообщения. С ней появляется риск, что инцидент отложат и забудут. Возможное решение: откладывание с обязательным комментарием, который виден в карточке и в журнале, и предельным сроком.

**13.7. Судьба колонки «История».**
Колонка из 20 отметок в списке доменов не несёт информации, которой нет в карточке, и вводит вторую ось (последовательность проверок) рядом с временной осью реестра. Проверить на пользователях, помогает ли она на самом деле; если нет — убрать, освободив место под возраст открытого расхождения.

**13.8. Наименование статуса.**
Статус «Решён» / «Не решён» рискует прочитаться как «отрезолвился» / «не отрезолвился», а для этого уже есть отдельное состояние домена. Альтернативы: «Совпал / Не совпал», «В списке / Вне списка». Решение за заказчиком; менять недорого, но менять нужно **до** релиза, потому что термин уйдёт в тексты уведомлений.

## 14. Критерии приёмки

Каждый пункт — сценарий автотеста.

### Проверка и статусы

1. Домен отдаёт три адреса, все входят в подсеть списка → статусы «Решён», событий нет, уведомлений нет.
2. Домен отдаёт адрес вне списка → статус «Не решён», открывается инцидент, порождается `NOT_ALLOWED`, уходит одно уведомление.
3. Тот же нерешённый адрес держится ещё пять проверок → повторных уведомлений нет, инцидент один.
4. Адрес совпадает с записью без маски → статус «Решён», в интерфейсе показано «входит в <запись>».
5. IPv4-адрес и запись IPv6 в списке → совпадения нет.

### Порог актуальности

6. Домен отдаёт по кругу два адреса из трёх, порог 24 часа, период 5 минут → актуальный набор постоянно содержит три адреса, событий `ADDRESS_APPEARED` и `ADDRESS_GONE` не порождается ни одного.
7. Один из трёх адресов перестал отдаваться, прошло меньше порога → адрес остаётся «Решён», событий нет.
8. Прошло больше порога → ровно одно событие `ADDRESS_GONE`, статус «Не актуален».
9. Адрес вернулся после того как стал неактуальным → событие `ADDRESS_APPEARED`.

### Резолв

10. Домен возвращает `NXDOMAIN` меньше N раз подряд → события нет.
11. N раз подряд → одно событие `RESOLVE_FAILED`, дальше не повторяется.
12. Все DNS-серверы недоступны → реестр не изменился, статусы не изменились, уведомлений нет, зафиксирована техническая ошибка.
13. Первый сервер в списке не ответил, второй ответил → результат взят со второго.

### Уведомления

14. Режим «Не уведомлять» → журнал заполняется, сообщения не уходят.
15. Режим «При изменении адресов» → `NOT_ALLOWED` уведомления не порождает.
16. Режим «При выходе из разрешённых» и пустой белый список → уведомлений нет никогда; интерфейс показывает предупреждение.
17. `BACK_TO_NORMAL` уходит ответом на сообщение об открытии инцидента и содержит длительность.
18. Комментарий домена пуст, комментарий группы заполнен → в сообщение попадает комментарий группы.
19. Оба пусты → строки комментария в сообщении нет.
20. Домен с 30 адресами → список в сообщении сокращён, комментарий не сокращён, сообщение укладывается в лимит.

### Наследование

21. Группа с периодом «по умолчанию» → домен проверяется с общим периодом.
22. Изменение общего периода → домены групп со значением «по умолчанию» подхватывают его, домены групп со своим значением не меняются.
23. Домен без группы → все наследуемые параметры берутся из общих настроек.
24. Удаление группы → домены остаются, переходят в «без группы», их белые списки не тронуты.

### Ввод

25. Импорт с ошибочной строкой → корректные строки добавлены, ошибочные остались в поле ввода.
26. Импорт домена, который уже есть, с выключенным флагом обновления → домен пропущен, его настройки не изменились.
27. Кириллический домен в импорте → предложен punycode или показана ошибка, молчаливого искажения нет.
28. Перенос домена в группу с другим режимом → показана сводка изменений до подтверждения.

### Базовая проверка и лавины

34. Импорт 200 доменов с включённым флагом «проверить сразу» → ни одного уведомления об изменении адресов, 200 записей `WATCH_STARTED` в журнале.
35. Домен выключен на срок дольше порога актуальности и включён снова → проверка базовая, событий изменения нет.
36. Сервис остановлен дольше порога актуальности и запущен → базовые проверки по всем доменам, лавины уведомлений нет.
37. Домен выключен на срок **короче** порога и включён снова → проверка обычная, базовой не считается.
38. На базовой проверке домен отдаёт адрес вне списка → инцидент открыт, статус виден в интерфейсе, уведомление доставлено в составе сводки, а не отдельным сообщением.
39. Шесть событий одного типа за 60 секунд при пороге слияния 5 → одно сводное сообщение, шесть записей в журнале.

### Напоминания

40. Открытый инцидент держится 7 часов при интервале 6 часов → ровно одно напоминание, отправленное ответом в исходную ветку.
41. За время между напоминаниями добавился ещё один нерешённый адрес → уходит сообщение о новом адресе, отдельное напоминание не отправляется.
42. Интервал «не напоминать» → напоминаний нет, сообщение о закрытии инцидента приходит.
43. Инцидент закрыт → напоминания прекращаются немедленно.

### Ввод белого списка

44. Ввод `10.20.999.0/24` → строка подсвечена, причина показана, сохранение заблокировано.
45. Ввод `10.20.3.7` при наличии `10.20.0.0/22` → предупреждение о перекрытии, сохранение разрешено.
46. Запись без маски совпала с адресом → в интерфейсе «точное совпадение с 10.20.3.7», формулировка «входит в» не используется.

### Ручная проверка и выгрузка

47. «Проверить домены группы» дважды подряд → вторая попытка отклонена кулдауном.
48. Ручная проверка домена → время следующей плановой проверки сдвинуто.
49. Выгрузка журнала с применённым фильтром → в файл попали только отфильтрованные строки, файл открывается в Excel без ручного импорта.

### Окружение и Redis

50. `AUTH_2FA_ENABLED=false` → на экране входа два поля, разметки поля кода нет в ответе сервера.
51. `AUTH_2FA_ENABLED=true`, у участника фактор не привязан → после верного пароля обязательная привязка, доступа к другим экранам нет.
52. Повторная отправка того же кода TOTP → отказ.
53. Не задана обязательная переменная окружения → приложение не стартует и пишет, какой именно переменной не хватает.
54. Обход всех ключей Redis после прогона основных сценариев → у каждого ключа задан срок жизни.
55. Полная очистка Redis → домены, события, реестр и участники целы; счётчики, кулдауны и блокировки сброшены.
56. N неудачных попыток → вход заблокирован; через 15 минут блокировка снята без участия приложения.
57. Счётчик неудачных попыток: 4 попытки, пауза 16 минут, ещё 4 попытки → блокировки нет, окно фиксированное.
58. Два экземпляра сервиса запущены одновременно → каждый домен резолвится один раз, уведомления не дублируются.

### Кэш и авария Redis

59. Изменён белый список домена → следующая проверка использует новый список, не дожидаясь истечения срока кэша.
60. Изменён период в группе → следующая проверка домена идёт по новому периоду.
61. Участник отключён → доступ прекращается не позже чем через 30 секунд.
62. Сброшено пространство `cache:*` под нагрузкой → сервис продолжает работать, блокировки планировщика и счётчики попыток не затронуты.
63. Достигнут предел памяти Redis → вытесняются только ключи кэша, ключи рабочего состояния целы.
64. Redis недоступен → проба работоспособности нездорова, интерфейс отвечает `503` с указанием причины, проверки доменов остановлены, запись в журнале есть.
65. Redis недоступен → уведомление об аварии доставлено в канал, хотя очередь и окно слияния недоступны.
66. Redis восстановлен после простоя дольше порога актуальности → проверки базовые, лавины уведомлений нет.

### Sentry

75. `SMTP_HOST` не задан → способ приглашения письмом выключен, на вкладке участников виден баннер с именами переменных, кнопки подключения почты нет.
76. `SMTP_HOST` задан → способ приглашения письмом доступен, состояние канала показано как настроенное.
77. Задан `SMTP_USER` без `SMTP_PASSWORD` → приложение не стартует и называет недостающую переменную.
78. Почтовый сервер задан, но недоступен → приложение стартует; неудача отправки письма фиксируется и уходит в Sentry после исчерпания повторов.
79. Наблюдатель или администратор через API пытается изменить параметры подключения почты → таких полей в API нет.

67. `SENTRY_DSN` не задан → приложение стартует и работает, попыток отправки нет.
68. `SENTRY_DSN` задан в неверном формате → приложение не стартует и называет переменную.
69. Redis недоступен → событие ушло в Sentry с меткой отказавшего компонента, и одновременно уведомление ушло дежурным.
70. Домен вернул `NXDOMAIN` → в Sentry ничего, в журнале событий запись есть.
71. Введён некорректный CIDR, отклонён импорт, не удался вход → в Sentry ничего.
72. Недоступны все DNS-серверы при обходе 500 доменов → в Sentry одно событие с числом затронутых доменов, а не 500 событий.
73. Sentry недоступен → проверки идут, уведомления доставляются, работа не нарушена.
74. В отправленном событии отсутствуют токен бота, строки подключения, хеши паролей и почтовые адреса участников.

### Редактирование участника
